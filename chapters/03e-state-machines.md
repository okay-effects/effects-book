# 3e · The compiler writes the state machine

The fifth family gets direct style without asking the runtime for anything. The program is written as
straight-line code and *transformed*, before it runs, into a value with one state for each place it can stop.
The rest of the program is then that value: plain data, with a function that steps it.

Every reader has used this family, because `async`/`await` is it. What is less often noticed is that the
transform does not care what the stops are for.

Four renderings run here. Two do the transform by hand, so that its result can be read: `code/rust/bank.rs`,
which this chapter follows, and `code/zig/bank.zig`, the same machine in a language with no closures at all.
Two use a transform their compiler already has: `code/csharp/bank.cs` on C#'s iterators, and
`code/kotlin/bank.kt` on Kotlin's `suspend`.

## What it is

The program one would like to write:

```rust
fn pay(from, to, amount) -> String {
    let have = ask(Balance(from));
    if have < amount { ask(Refuse(format!("{from} has {have}, needs {amount}"))) }
    ask(Move(from, to, amount));
    let at = ask(Now);
    format!("moved {amount} from {from} to {to} at {at}")
}
```

(That listing is the comment at the top of the type in `bank.rs`; it is not compiled.) What it becomes: an
enum with a variant for each `ask`, holding the variables that are still needed after it, and one function
that continues from a variant with an answer.

```rust
#[derive(Clone, Debug)]
enum Pay {
    Start { from: String, to: String, amount: i64 },
    AtBalance { from: String, to: String, amount: i64 },
    AtRefuse,
    AtMove { from: String, to: String, amount: i64 },
    AtNow { from: String, to: String, amount: i64 },
}

enum Step {
    Ask(Op, Pay),
    Done(String),
}

impl Pay {
    fn step(self, answer: Answer) -> Step {
        match (self, answer) {
            (Pay::AtBalance { from, to, amount }, Answer::Number(have)) if have < amount => {
                Step::Ask(Op::Refuse(format!("{from} has {have}, needs {amount}")), Pay::AtRefuse)
            }
            (Pay::AtBalance { from, to, amount }, _) => {
                Step::Ask(Op::Move(from.clone(), to.clone(), amount), Pay::AtMove { from, to, amount })
            }
            // … one arm per state
        }
    }
}
```

`Step::Ask(op, rest)` is chapter 2's pair, literally: a question, and the rest. But the rest is not a function.
It is a value of type `Pay`, such as `Pay::AtMove { from: "ann", to: "bob", amount: 30 }`, and it says in so
many words where the program is and what it remembers. The interpreter is a short loop:

```rust
fn run(handlers: &mut [&mut dyn Handler], mut step: Step) -> Outcome {
    loop {
        match step {
            Step::Done(receipt) => return Outcome::Paid(receipt),
            Step::Ask(op, rest) => match answer(handlers, &op) {
                Ok(a) => step = rest.step(a),
                Err(outcome) => return outcome, // `rest` is dropped here: Rust frees what it held
            },
        }
    }
}
```

The technical name for writing a function's continuations as the cases of a data type is
*defunctionalisation*. The state machine is the defunctionalised rest.

## What it gives

**The rest is data, so it can be copied.** `#[derive(Clone)]` on the enum is the whole of multi-shot. Line 6 of
the scenario stops the program at `Balance`, clones the rest, and steps each copy with a supposed answer:

```rust
let Step::Ask(Op::Balance(_), rest) = start(pay("ann", "bob", 30)) else { unreachable!() };
// for each supposed balance:
let copy = rest.clone().step(Answer::Number(supposed));
```

No replay, no reflection, no runtime. The four renderings whose source reads as direct style cannot resume
twice. This is the form that would let them, if something did the transform for them.

**The rest is data, so it can be stored.** A value of `Pay` has no pointer into a stack and no closure. It can
be printed (the rendering derives `Debug`), and a serialiser for it is a derive away. I have not run that here.
Axis (g) is open in this family and in almost no other; what it then costs is versioning, since a stored
`AtMove` must still mean something after `pay` is edited.

**No allocation, no garbage collector, no runtime.** A step is a `match` and a move. This is why the family is
the one that languages without a collector use, and why it is the fastest in the measurements I have. From my
Rust library, with its protocol — microseconds per run of a thousand operations, three alternating rounds,
medians, 2026-10-28, on a machine under other load: every path of a choice among 1000 took 0.28 µs as a
state machine generated by an attribute, against 13.24 µs for the same lane on a machine over a tree on the
JVM; a handler taking the rest at each of 1000 steps, 0.62 against 9.44 (`okay-rust/README.md`). My Zig port
reports the same shape inside one language: 0.38 µs against 29 µs through its own machine
(`okay-zig/README.md`). Different languages are being compared in the first pair, so it is a magnitude and no
more; the second pair is one language and one author.

**Straight code for the optimiser.** Each state's continuation is ordinary code up to the next stop. Nothing is
dispatched through a general loop.

**Ownership works out.** When the loop above drops `rest` on a refusal, Rust frees what the program held at
that point. Leaving early (axis f) is the language's destructors, with nothing added.

## What it costs

**Somebody must do the transform**, and each of the three candidates has a cost.

*By hand.* `Pay` is five variants for a function of five lines, and each edit to the function is an edit to
the enum, the arms, and which variables each state carries. It is exact and it does not scale to a codebase.
My Zig port writes its resumable programs this way, because there "comptime cannot rewrite a function's body"
(`okay-zig/specs/design.md`) — the states are by hand, "the shape Rust's `#[resumable]` and Goose's okgc
generate" (`okay-zig/README.md`).

*By a macro, an attribute or a compiler plugin that you own.* Then the source is direct style again. The price
is that the transform supports a subset of the language and says no to the rest. Of my own Rust attribute:
it lowers `if`, `while`, `loop`, `match` arms, blocks and `return`, and "a stop inside an expression, a `for`
holding a stop and type parameters are errors saying so" (`okay-rust/README.md`). Error messages point at
generated code unless care is taken. Recursion needs indirection, because a state that contains itself has no
finite size.

*By the language.* Then it is robust, supported by tools, and usually fixed to one purpose, which is the next
section.

**Colour.** A function that may stop is a different kind of thing from one that may not, and its callers must
be transformed too.

**Values that live across a stop must be owned by the state.** A reference into a local variable cannot
survive being moved into an enum. The hand-written rendering clones two strings to avoid the question. Rust's
own `async` solves it with pinned, self-referential futures, which is a large part of why they are hard to
write by hand.

## `async`/`await` is this family with one effect

`async`/`await` in Rust, C#, Kotlin (`suspend`), JavaScript, Python and Swift is the same transform — or, in
the interpreted languages, the same idea done by the engine — with the stops reserved for one question, "wait
for this", and the handler fixed to be a scheduler.

Two questions decide how much of chapter 2 can be recovered from it.

*Can user code be the handler?* If a library may drive the state machine itself, instead of handing it to the
platform's scheduler, then `await` becomes a general "ask". Rust allows this: a future is a value with a `poll`
method, and anyone may poll it. Kotlin allows it: the standard library exposes the continuation of a `suspend`
function. My Rust and Kotlin libraries both build on exactly these (`okay-rust/README.md`: a program "is an
`async` block: a state machine the compiler builds"; `okay-kotlin/docs/design.md`).

*Can user code see inside the state?* Usually not, and that is what is lost relative to the hand-written enum.
A Rust future is an opaque type: it cannot be cloned or inspected, so effects built on `async` are one-shot.
My library says so and keeps a second route for the other case: "An `async` body's future cannot be cloned, so
the one API is one-shot; a program whose rest is taken many times is a RESUMABLE fn — its rest an explicit
`Clone` value" (`okay-rust/README.md`). Kotlin's continuation is an ordinary object on the JVM, which is why
the frame-copying of chapter 3d is possible there at all.

So a language's `async` is a ready-made, well-supported state machine transform that gives one resumption and
no storing. Where that is enough it is the best substrate available in that language, because the compiler
team maintains it.

The two renderings on a compiler's own transform show both answers.

`code/kotlin/bank.kt` uses nothing but the standard library. An effect is an interface of `suspend` functions;
the handler for refusals takes the program's continuation with `suspendCoroutineUninterceptedOrReturn`, does
not resume it with a value, and resumes it with an exception so that the body unwinds:

```kotlin
override suspend fun refuse(why: String): Nothing =
    suspendCoroutineUninterceptedOrReturn { rest ->
        outcome = "refused: $why"
        dropped = rest
        COROUTINE_SUSPENDED
    }
```

For line 6 it takes the rest at `balance` and resumes it twice. The first resumption runs the program to its
end. The second fails inside the coroutine machinery, with no message about resuming twice: the continuation
is a mutable object that has moved on, and the standard library's raw interface does not guard it. The
rendering prints *cannot*, and that failure is the reason frame-copying exists.

`code/csharp/bank.cs` uses the oldest compiler-made state machine in the mainstream, the iterator. `yield
return` hands a question out. It cannot receive an answer, so the answer is written into the question object
before the iterator is stepped again, and the program's result leaves through a callback. Leaving early is
`Dispose` on the enumerator, which runs pending `finally` blocks. The state machine is a class the compiler
generates and the language gives no access to; there is nothing to copy. C#'s `async` is the same machinery
with a slot for the answer, and is what a library would build on.

## The transform applied after the compiler

There is a fourth candidate for "who does the transform": a tool that rewrites compiled code. On the JVM a
method can be rewritten so that, at a question, it saves its local variables into an object and returns, and
can later be entered again at that point with the variables restored. The technique is in the literature as
"continuations from generalized stack inspection" (Pettyjohn, Clements, Marshall, Krishnamurthi, Felleisen,
ICFP 2005). One of my Java modules does it with the class-file API of the JDK. The source stays plain Java
with no marker on its methods. The saved frames are data, so they can be re-entered more than once. Its
restrictions are the kind every transform has: an effect there "cannot have type arguments", and "a monitor
cannot be saved" (`okay-java/resumable/README.md`). In the same table as chapter 3d's figures, a handler that
takes the rest and resumes it once cost 57.1 ns through saved frames, against 110 ns through the JDK's
continuation and 20.1 ns on a machine over a tree.

In Scala, `dotty-cps-async` is a macro of this family for a different target: it turns direct-style code
inside an `async` block into calls on a monad. Java has no macros, but javac takes plugins, and a plugin can
do the same before types are checked: okay-tiny's turns `$(program)` in a method marked `@Direct` into the
`flatMap` chain over its tree, so the row and the inference are javac's (chapter 3j). It works on javac's
internal classes, as Lombok does. So in Java the transform need not be applied after the compiler.

## The handler, in this family

A detail of `bank.rs` that should not pass unremarked. Its handlers do not receive the rest as something they
can call. They return a *reply* — pass, resume with this, leave with that, ask this instead — and the loop
acts on it:

```rust
enum Reply {
    Pass,            // not mine; I am shown the answer on its way back (`seen`)
    Resume(Answer),  // the rest goes on with this
    Leave(Outcome),  // the rest is dropped
    Instead(Op),     // ask this of whoever is outside, in its place
}
```

That is the handler's side defunctionalised as well: the things a handler may do with the rest, as data. It
covers the scenario and it is how answers stay in place with no capture. It does not cover a handler that
wants to run the rest and then look at what came back, which chapter 6 needs; for that the handler must be
given the rest as a value, as line 6 does explicitly. A library offers both, and the cheap one by default.

To be exact about what is and is not expressible in the three renderings of this chapter that answer this way
(`bank.rs`, `bank.zig`, and `bank.cs`, whose handler returns "mine, with this answer" or "not mine" and leaves
by throwing). Through the handler interface: answer, refuse, substitute a question, and see an answer on its
way back (the `seen` hook in Rust; the journal's call to the handlers outside in C#). Not through it: continue
the program and then act on how it *ended* (section 6.4), or keep the rest for later (6.3, 11.1). In Rust and
Zig both are still possible, one level up: the code that drives the machine holds `rest` as a plain value —
line 6 takes it out of `Step::Ask` and steps two copies — so a driver can run the rest to its outcome and then
do what a handler would have done. In C# the rest is the enumerator, which the driver holds and can step
later but cannot copy. No line of the scenario exercises either, so this paragraph is read from the three
files and not run; section 6.8 has the table for all sixteen renderings.

## On the axes

| axis | this family |
| --- | --- |
| b. the rest | a defunctionalised value: an enum of states (or an opaque future, for the language's own `async`) |
| c. finding the handler | whoever steps the machine: a stack of handlers, or evidence passed in |
| d. the types | the host's; the answer type is erased unless the transform generates one per stop |
| e. resumptions | many if the state can be copied; one for an opaque future |
| f. leaving early | drop the state: destructors where the language has them, otherwise finalizers as data |
| g. storing the rest | yes, if every field can be written; then versioning |
| h. cost | no allocation; straight code per state |
| i. the host | coloured functions; traces show the step function; `async` runtimes are the same machinery |

**Choose it when** the path is hot, or there is no garbage collector, or the rest must be copied cheaply or
written down — and a transform exists for your language or you are prepared to own one. **Use the language's
own `async` as the substrate when** one resumption is enough and its scheduler can be replaced or shared.
**Do not write the states by hand** beyond a few small workflows whose states are the point, such as the
approval of chapter 11.
